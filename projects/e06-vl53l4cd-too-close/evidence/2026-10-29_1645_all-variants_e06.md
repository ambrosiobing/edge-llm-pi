**This file closes no clause of e06 and none of these runs is a measurement of the project.**
All three of e06's acceptance quantities come from the sensor during 200 hand approaches at
three speeds, and no approach has been made. What follows is every variant run while getting
there, in one place, with the differences between them attributed where they can be and marked
confounded where they cannot.

It exists because six runs were made in an afternoon with four things changing between them,
and a reader finding two of those numbers in isolation would reasonably conclude something
false from the difference.

## The two wirings

**Wiring one.** Four leads to header pins 1, 3, 5 and 9. **Two of the four were the same dark
blue**, which no colour column can disambiguate. Verified: `i2cdetect` returned 0x29 alone.
Runs 4 and 5 were taken on it.

**Wiring two.** The same four pins, recoloured so each lead is distinct: blue VIN, violet SDA,
red SCL, green GND. Verified again from scratch: `i2cdetect` 0x29 alone, plus run 6's 104
samples with zero bad statuses. Recorded in `wiring.md` with the photograph.

**The rewire invalidated the earlier verification and that is not a formality.** Every jumper
was pulled and replaced. A swapped lead does not fail loudly on I2C: it gives silence, which
is indistinguishable from a sensor nobody is asking. So the bus check and a ranging run were
both repeated rather than carried over. Runs 4 and 5 belong to a wiring that no longer exists;
their sensor behaviour is still informative, their lead identities are not.

**Why recolour at all, when the first wiring worked.** Because e03's wiring had two identical
yellow leads, and on Tuesday 27 October 2026 its three modules went in one position out:
yellow on GPIO17, red on GPIO27, nothing on GPIO22. That was caught only by driving each line
by hand before the run. e03's own file now recommends a third colour; this is that
recommendation applied before rather than after.

## The ULD, which has one assembly variant

The package ships the four files e06's CMake needs in **two different directories**, and the
configure refuses unless they sit together:

    VL53L4CD_ULD_V2.2.3/VL53L4CD_ULD_Driver/   VL53L4CD_api.c  VL53L4CD_api.h  VL53L4CD_calibration.c
    VL53L4CD_ULD_V2.2.3/Platform/              platform.h

Copying `platform.h` beside the driver is the whole of it. A second `platform.h` exists under
`CubeIDE_Example/Core/Inc/` at a different size, 1772 bytes against the generic 1746; the
generic one is the right one, since e06 supplies its own implementation in
`src/vl53l4cd_platform.c`. The `stm32duino/VL53L4CD` mirror is also permissively licensed but
ships the driver as `.cpp` with no `platform.h`, so it is not a substitute.

## WHAT DIFFERS BETWEEN THE RUNS, AND WHY

### Runs 1 and 3: the only controlled pair here

Same board, same thread count, same replay, same fifty events. **One variable: `--n-predict`.**

    1  default budget   prompt 4359.2   generate  907.5   agreement.py: 50 of 50 not a decision
    3  --n-predict 64   prompt 4388.0   generate 4123.9   agreement.py:  0 of 50 not a decision

**Generation rose 4.5 times and the prompt did not move**, 4388.0 against 4359.2, a difference
of 0.7 percent. That is the signature of a budget change and nothing else: the prompt half
cannot be affected by how many tokens are allowed out.

Run 1's answers were all cut at the same 23 characters, `{ "decision": "APPROACH`, about seven
tokens. `json.loads` cannot parse an unterminated object, so `agreement.py` fell back to the
raw string, which matches no rule literal, and correctly reported all fifty rows as not a
decision. **The tool was right and the invocation was wrong.** `--n-predict` was simply
omitted; e03 and e04 both pass 64.

### Runs 1 and 2: board and thread count, confounded

    1  board A  2 threads     prompt 4359.2   generate  907.5
    2  board B  default thr   prompt 5747.0   generate 1504.7

Prompt 1.32 times, generation 1.66 times. **Neither ratio can be attributed**, because the
board and the thread count both changed and run 2's thread count was never specified, so it
took whatever the binary defaults to. This pair is listed for completeness and should not be
quoted for anything.

### Runs 3 and 5: the figures most likely to be misread

    3  board A  2 threads  replay   prompt 4388.0   generate 4123.9
    5  board B  4 threads  live     prompt 5066.8   generate 7172.5

Three variables at once: board, thread count, and replay against live. **Confounded three
ways.** The temptation is to read 7172.5 against 4123.9 as a board figure; it is not.

What *can* be said comes from measurements made elsewhere on Tuesday 27 October 2026 with one
variable each: the A72 leads the A53 by 2.58 on prompt and 2.02 on generation, and two extra
threads buy 1.94 on prompt and 1.14 on generation. Those were measured on e03 with everything
else held still. Applying them to run 5 projects board A at four threads near 5.5 s total,
which is an estimate and is labelled as one everywhere it appears.

### Runs 4, 5 and 6: why two of them asked the model nothing

This is the finding that changes how the afternoon must be run, and it looked like a fault.

e06 asks the model **only on a sample still fresh**, at most 2.5 sampling intervals old. The
sampler is a child process writing ten rows a second into a pipe, and it starts before the
model loads. Twenty-five seconds of model loading therefore builds a backlog of roughly 250
rows before the loop reads its first one.

    4  --max-events 10     the loop never got past the backlog      0 answers
    6  --max-events 20     same                                     0 answers
    5  --max-events 1000   drained it, then asked repeatedly        8 answers

So runs 4 and 6 report `mean prompt 0.0 ms`, which is not a stall and not a wiring fault: it
is the gate declining to ask about rows half a minute stale. **The arithmetic that matters:
run 5 gives one answer per 125 samples**, which at ten samples a second means e06 needs about
25,000 samples, roughly 42 minutes of continuous sampling on board B, to reach the two hundred
model-answered rows its acceptance wants.

### Resident memory, which splits cleanly along one line

    runs that produced no model answer   315808, 315804 kB   about 308 MiB
    runs that produced answers           329608 to 353500    322 to 345 MiB

About 15 to 37 MiB more once a generation has actually run. The model file is memory mapped in
both cases, so this is the decode path's own allocation appearing only when it is first used.
Worth knowing because a resident-memory figure taken from a run that never generated would
understate the project by a tenth.

## WHAT DOES NOT DIFFER, ACROSS EVERY VARIANT

**The sensor never failed.** 346, 1120 and 104 samples across three live runs and two
wirings: **zero with a range status other than 0**. No dropped frames, no bad statuses, on
either wiring.

**The model always says APPROACHING.** Fifty times on replayed data where the rule said CLEAR
33 times, and eight times on live data where the rule said TOO_CLOSE every time, with a
stationary object about 40 mm from the sensor. Nothing was approaching, and 40 mm is far
inside the 300 mm line.

Two distributions, two boards, two sources, one answer. **This is e04's failure in a second
project**: e04 scored 42.2 percent and never once emitted its third class across fifty-one
events that called for it. The prediction on record, written before the afternoon rather than
after it, is that e06's agreement will resemble e04's rather than e03's 100.0 percent, and
will approximate whatever share of the rule's decisions happen to be APPROACHING.

## A TRAP THAT FIRED TWICE AND IS NOT A DEFECT

`agreement.py` reported `not a decision of the rule` for valid answers in two different runs,
for two different reasons:

    run 1   the objects were truncated, so no decision could be parsed at all
    run 5   the answers were valid, but the rule never emitted APPROACHING in that log

The second is the documented limit of inferring the vocabulary from one log. The tool's own
source says so: "the limit of that choice is a log whose rule never used one of its names,
where a model answering that name would be reported as malformed", and adds that a log short
enough for the risk to be real is short enough to read by eye. Two hundred approaches at three
speeds will exercise all three names.

Worth the contrast: **this tool documents its blind spot at the point of the blind spot**,
where e04's client printed `no literal 0` and documented nothing, which concealed 136 unclosed
objects for a week until somebody counted them by hand.

## Deviations

1. **Runs 4 to 6 ran on a Pi 3B+ Rev 1.3, not the Pi 3 Model B Rev 1.2 the chapter
   allocates**, and runs 1 and 3 on a Pi 4B, which is further still. Same bus and, for the
   3B+, the same memory class.
2. **The sensor is on a breadboard**, not on the flying leads the chapter describes.
3. **The chapter's own dry run uses `--stub`**, which neither board can do, both being built
   with the real engine. The real model was used instead, and that is the closer rehearsal: a
   stub can neither truncate an object nor collapse to one literal, which are the two things
   these runs actually found.
4. **Runs were made as `bing` from a root login on board A**, not through any service unit.
